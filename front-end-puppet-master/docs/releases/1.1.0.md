# Release 1.1.0

Date: 2026-02-20  
Type: Minor (`1.0.0 -> 1.1.0`)

## Versioning Decision

`1.1.0` is correct because:

1. `1.0.0` already exists in `CHANGELOG.md`.
2. This release is additive/hardening-focused.
3. No intentional framework-wide breaking contract was introduced.

## Exact Change Ledger (Feature by Feature, Fix by Fix)

Every item below is written as: `Before -> After -> Upgrade impact`.

### 1. Roles API Canonicalization and Audit Fixes

`RLS-001` Files: `server/api/admin/roles.get.ts`, `server/api/admin/roles.post.ts`  
Before: Duplicate top-level route handlers existed alongside nested route handlers for the same endpoint family.  
After: Duplicate top-level handlers were removed; canonical handlers are under `server/api/admin/roles/index.*.ts`.  
Upgrade impact: If your project copied/overrode the deleted top-level files, switch to the `index.*` handlers to avoid route ambiguity.

`RLS-002` File: `server/api/admin/roles/index.get.ts`  
Before: Response returned only `{ roles }`.  
After: Response now returns `{ success: true, roles }`.  
Upgrade impact: Frontends expecting only `roles` continue to work, but strict response validators should accept `success`.

`RLS-003` File: `server/api/admin/roles/index.post.ts`  
Before: `audit.roleCreate(...)` was called with incomplete arguments.  
After: Full payload is passed: `event, actorUserId, roleId, roleName, roleSlug`.  
Upgrade impact: Audit trail now records role creation with complete metadata.

### 2. FAQ Data Integrity and Stored XSS Hardening

`FAQ-001` File: `server/api/admin/faq/index.post.ts`  
Before: FAQ item creation did not guarantee a valid required `slug`; question/answer validation allowed empty strings; FAQ text was not sanitized at write-time.  
After: Added slug generation (`slugify`), uniqueness loop (`createUniqueSlug`), stricter `min(1)` for question/answer, HTML escaping for question/category, and HTML sanitization for answer.  
Upgrade impact: Existing create clients can continue calling the endpoint, but content now goes through sanitization and slugs are guaranteed.

`FAQ-002` File: `server/api/admin/faq/[id].put.ts`  
Before: Update payload attempted to set `updatedAt` on `faqItems` although this column is absent; translations were not sanitized; validation allowed empty strings.  
After: Removed invalid `updatedAt` write; added sanitize/escape for updated fields; added `min(1)` validation for translation question/answer.  
Upgrade impact: Prevents runtime DB errors and enforces safer/non-empty FAQ translations.

`FAQ-003` File: `server/api/admin/faq/[id]/translations.put.ts`  
Before: Manual/partial validation only; missing strict schema and no required "at least one field" guard; no sanitization on write.  
After: Added Zod schema with `locale` bounds, optional nullable `question/answer`, refinement requiring at least one of them, plus sanitize/escape write path.  
Upgrade impact: Invalid payloads now fail fast with structured validation errors.

### 3. Admin Settings Validation Sync

`SET-001` File: `server/api/admin/settings.put.ts`  
Before: Backend used a hardcoded allowlist of keys that could drift from config/UI definitions.  
After: Allowed keys are derived from `config.settings.map(setting => setting.key)` from `app/puppet-master.config.ts`.  
Upgrade impact: API acceptance now tracks framework config automatically; custom settings keys must exist in config.

### 4. Audit Log Filtering Accuracy

`AUD-001` File: `server/api/admin/audit-logs.get.ts`  
Before: Filter conditions were assembled but not consistently applied to both `total` and paginated log query.  
After: Added proper `whereClause` (`and(...)` when needed), applied it to count and list queries, and added `success: true` in response.  
Upgrade impact: Pagination metadata now correctly matches filtered result sets.

### 5. Setup Workflow and AI Workflow Selection

`SETUP-001` File: `server/api/setup/config.post.ts`  
Before: Setup config schema did not include `aiWorkflow`; write/validation path did not verify workflow writeback.  
After: Added `aiWorkflow` to schema and config apply flow, then validated persisted value and rollback on mismatch.  
Upgrade impact: Setup now supports explicit workflow selection (`claude|qwen|codex`) with safer persistence checks.

`SETUP-002` File: `server/api/setup/config.post.ts`  
Before: Project brief write path was coupled to `.claude-data`.  
After: Brief write path now uses selected workflow data directory (`.claude-data`, `.qwen-data`, `.codex-data`) via utility functions.  
Upgrade impact: Multi-workflow projects now store setup artifacts in the active workflow namespace.

`SETUP-003` File: `server/api/setup/config.post.ts`  
Before: Workflow data dir existence was not enforced before writing brief files.  
After: Added `ensureWorkflowDataDir(...)` and explicit setup error if directory initialization fails.  
Upgrade impact: Fewer silent setup failures in fresh environments.

`SETUP-004` File: `server/api/setup/config.post.ts`  
Before: Backup cleanup used empty `catch {}` blocks.  
After: Cleanup blocks are explicit and lint-safe with documented ignore comments.  
Upgrade impact: No behavior break; improved reliability and lint compliance.

`SETUP-005` File: `server/api/setup/config.get.ts`  
Before: Setup summary did not return current `aiWorkflow`; project brief read path was workflow-agnostic.  
After: Returns `aiWorkflow`, resolves brief path by workflow directory, and now uses correct path root (`process.cwd()/.<workflow>-data/project-brief.md`).  
Upgrade impact: Init UI can reliably load selected workflow and related brief metadata.

`SETUP-006` File: `server/api/setup/import-zip.post.ts`  
Before: Cleanup in error paths used empty catch blocks.  
After: Explicit cleanup error handling comments and maintained cleanup flow.  
Upgrade impact: No external contract change; cleaner and safer maintenance path.

### 6. Workflow Path Utility and CLI Support

`WFLOW-001` File: `server/utils/workflow-paths.ts` (new)  
Before: No centralized typed utility for workflow path resolution/validation.  
After: Added typed helpers for current workflow detection, workflow directory mapping, directory validation, and workflow data dir initialization.  
Upgrade impact: Setup and other workflow-aware endpoints can use a single source of truth.

`WFLOW-002` File: `scripts/switch-workflow.ts` (new), `package.json`  
Before: No first-party CLI to switch `aiWorkflow` and bootstrap directories.  
After: Added `npm run workflow:switch -- <claude|qwen|codex>` to update config and provision workflow folders/config skeleton.  
Upgrade impact: Safer workflow switching without manual config edits.

`WFLOW-003` File: `scripts/workflow-info.ts` (new), `package.json`  
Before: No first-party CLI to inspect active workflow state.  
After: Added `npm run workflow:info` to print current workflow, mode, and workflow directory health.  
Upgrade impact: Faster diagnostics for setup and team onboarding.

### 7. Config and Type Surface for AI Workflow

`CFG-001` File: `app/puppet-master.config.ts`  
Before: No top-level `aiWorkflow` field.  
After: Added typed field `aiWorkflow: 'claude' | 'qwen' | 'codex'` with documented purpose.  
Upgrade impact: Framework config now explicitly controls AI workflow.

`CFG-002` File: `app/types/config.ts`  
Before: No shared type alias for workflow selection.  
After: Added exported `AiWorkflow` type.  
Upgrade impact: TS consumers can share the same workflow type across UI/server/scripts.

### 8. Init Wizard UX for Workflow Selection

`INIT-001` File: `app/pages/init.vue`  
Before: Setup wizard did not expose workflow selection.  
After: Added workflow selection cards (Claude/Qwen/Codex), load existing workflow from config GET, and submit `aiWorkflow` in setup POST payload.  
Upgrade impact: Workflow choice is now explicit at setup time instead of implicit defaults.

`INIT-002` File: `app/assets/css/ui/content/init.css`  
Before: No style tokens/classes for workflow cards.  
After: Added `.workflow-cards`, `.workflow-card`, active/hover states, and check icon styles using framework tokens.  
Upgrade impact: No API impact; UI consistency for setup screen.

### 9. CSS Governance and Inline Style Removal

`CSS-001` Files: `app/components/atoms/AppImage.vue`, `app/assets/css/ui/content/app-image.css`, `app/assets/css/ui/content/index.css`  
Before: `AppImage` styles were embedded in the component.  
After: Removed component style block and moved classes to global CSS; imported new file in content CSS index.  
Upgrade impact: Aligns with PM global CSS-only rule; no expected visual regression.

`CSS-002` Files: `app/pages/admin/roles.vue`, `app/assets/css/ui/admin/pages.css`  
Before: Roles page carried its own style block and used non-standard tokens (`--c-success`, `--border-color`, `--bg-subtle`).  
After: Styles moved to global admin CSS under `.admin-roles` namespace and normalized to semantic tokens (`--d-success`, `--l-border`, `--l-bg-sunken`).  
Upgrade impact: Better theming consistency and rule compliance.

`CSS-003` Files: `app/pages/admin/login.vue`, `app/components/organisms/ChangePasswordModal.vue`  
Before: Error/help UI used inline styles.  
After: Replaced with semantic classes (`text-center`, `mb-4`, `text-danger`) and existing form utility classes.  
Upgrade impact: Cleaner class-based styling and easier overrides.

`CSS-004` Files: `app/components/loading/LoadingCard.vue`, `app/components/loading/LoadingText.vue`, `app/assets/css/ui/content/loading-placeholders.css`  
Before: Loading card title spacing and line spacing relied on inline styles/bindings.  
After: Added `.placeholder-card__title-placeholder` class and removed inline styles; line spacing now relies on existing `.placeholder-text { gap: 0.5em; }`.  
Upgrade impact: No behavior change expected; styling is centralized.

### 10. Tooling and Lint Stability

`TOOL-001` File: `vitest.config.ts`  
Before: Default Vitest reporters included `html`, which can fail when optional UI/report packages are not installed.  
After: Default is now `reporters: ['default']`.  
Upgrade impact: Test startup is more reliable in minimal environments; add HTML reporter manually if needed.

`TOOL-002` File: `server/utils/password.ts`  
Before: Special-character regex was complex and lint-noisy due escape-heavy pattern duplication.  
After: Replaced with `specialCharRegex = /[^A-Za-z0-9]/` and reused it for checks/scoring.  
Upgrade impact: Same policy intent, simpler and more maintainable implementation.

## Upgrade Actions (Project Maintainers)

1. Pull framework update and install dependencies:
```bash
npm install
```
2. If you customized role endpoints, remove/ignore legacy `server/api/admin/roles.get.ts` and `server/api/admin/roles.post.ts` overrides.
3. Ensure custom settings keys are declared in `app/puppet-master.config.ts` (`settings[]`) or API writes will be rejected.
4. Re-test FAQ content rendering with sanitized persisted values.
5. If your tests require HTML reports, add custom Vitest reporter config in your project (default now uses `default` reporter only).
6. If you use workflow switching, validate:
```bash
npm run workflow:info
```
7. Run validation pipeline:
```bash
npm run lint
npm run build
npm run test:run
```

## Contract Changes to Be Aware Of

1. `GET /api/admin/roles` now returns `success: true` in addition to `roles`.
2. `GET /api/admin/audit-logs` now returns `success: true` and accurate filtered pagination totals.
3. `PUT /api/admin/faq/:id/translations` now strictly validates input with Zod and rejects empty payloads.
4. `POST /api/setup/config` now accepts optional `aiWorkflow` and returns effective `aiWorkflow` in response.
5. `GET /api/setup/config` now includes `aiWorkflow` in setup summary payload.

## Breaking Changes

None intentionally introduced for standard usage patterns.

## Known Follow-Up

Some test suites can still fail in local environments with existing schema/env drift; this release fixes test runner startup reliability but does not refactor all legacy tests.
