## 2) Blocking issues (must be fixed/clarified upstream)

### B1. Config naming is misleading

Current release proposal:

- `features.websiteChromeWidth: 'contained' | 'full'`

Problem:

1. Name implies whole-website content width.
2. Actual behavior controls header/footer inner chrome width only.
3. It conflicts with existing mental model where page content/scenes can be full-bleed independently.

Required framework action:

1. Rename to a precise key, e.g.:
- `features.headerFooterWidthMode`
2. Keep backward compatibility alias for at least one minor release.
3. Add migration note and deprecation timeline.

### B2. Contained/full semantics must be explicit and unambiguous

Problem:

1. Team members interpret "contained" differently (full bar vs constrained block).
2. Release text can be read in two ways and causes product-level confusion.

Required framework action:

1. Add exact definitions in docs/config comments:
- `contained`: header/footer inner content constrained + centered.
- `full`: header/footer inner content edge-to-edge (no max-width).
2. Add visual examples (desktop, ultrawide).
3. Add explicit note that main content width/scrollytelling width are separate concerns.

### B3. Onepager scrollytelling must stay global (top-to-bottom timeline)

Problem:

1. Scrollytelling in onepager should feel continuous through full page scroll.
2. Scene rules must enhance, not split, narrative continuity.

Required framework action:

1. Document global timeline as non-negotiable contract for onepager.
2. Keep scene rules as additive local amplifiers only.
3. Add regression test that global `--pm-scroll-progress` works across full page height.

### B4. Full-bleed scene wrapper should be standardized (no manual template repetition)

Problem:

1. Requiring per-section manual full-bleed markup increases drift risk.
2. Teams will implement slightly different wrappers and break consistency.

Required framework action:

1. Officially standardize reusable wrapper class `scene-full-bleed`.
2. Auto-apply via shared renderer path (or equivalent centralized mechanism).
3. Add style contract test for this behavior in onepager sections.

### B5. Admin nav alignment contract must be formalized as framework rule

Problem:

1. Horizontal admin header left-biased nav hurts scanability.
2. UX expectation differs by mode (horizontal vs vertical), and this must be codified.

Required framework action:

1. Horizontal mode: nav cluster centered.
2. Vertical mode: nav top-anchored.
3. Add regression test/snapshot for both modes.
