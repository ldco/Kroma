# Release 1.2.0

Date: 2026-02-20  
Type: Minor (`1.1.0 -> 1.2.0`)

> Note: Follow-up contract clarifications and migration packaging are released in [`1.2.1`](./1.2.1.md).  
> If you are upgrading today, target `1.2.1`.

## Versioning Decision

`1.2.0` is correct because this release adds reusable framework capabilities, hardens existing behavior, and introduces no intentional API/schema-breaking change.

## Exact Change Ledger (Feature by Feature, Fix by Fix)

Every item below is written as: `Before -> After -> Upgrade impact`.

### 1. Mobile Header Actions Visibility Contract

`NAV-001` Files: `app/assets/css/skeleton/header.css`, `app/assets/css/skeleton/mobile-nav.css`  
Before: Under `--below-desktop`, `.header-actions` was hidden globally, which also hid action controls inside mobile drawer settings.  
After: Mobile hide rule is now scoped to top header context only (`.header-inner > .header-actions`), and drawer settings explicitly keep `.header-actions` visible.  
Upgrade impact: Mobile drawer theme/language/login actions are visible out-of-the-box without project-local overrides.

### 2. Layout Containment and Fixed Header Reliability

`LAY-001` File: `app/assets/css/layout/page.css`  
Before: Root wrappers `.layout` and `.layout-admin` used `contain: layout style`, which can break fixed-header viewport behavior in some engines.  
After: Root containment removed; containment remains on `.main` container-query host.  
Upgrade impact: Fixed header behavior is restored/consistent while preserving component-level containment.

### 3. Scrollytelling Runtime and Directive Baseline

`SCR-001` Files: `app/composables/useScrollytelling.ts`, `app/plugins/scrollytelling.ts`, `app/assets/css/animations/scrollytelling.css`, `app/assets/css/animations/index.css`, `app/layouts/default.vue`  
Before: Framework had reveal/scrollspy primitives but no reusable scrollytelling/parallax runtime.  
After: Added global onepager runtime with CSS hooks (`--pm-scroll-progress`, `--pm-scene-progress`, `--pm-parallax-x`, `--pm-parallax-y`), plus directives `v-parallax` and `v-scrolly-scene`; runtime is reduced-motion safe.  
Upgrade impact: Additive capability; existing pages keep current behavior unless using scene/parallax attributes/directives.

`SCR-002` Files: `app/components/organisms/SectionRenderer.vue`, `app/pages/index.vue`, `app/assets/css/layout/sections.css`  
Before: Section rendering had no standardized full-bleed scene wrapper for onepager storytelling.  
After: Onepager sections now auto-use shared `scene-full-bleed` scene wrappers via renderer/home usage and scene directive wiring.  
Upgrade impact: Onepager sections gain consistent full-bleed storytelling surface while keeping inner content constrained.

`SCR-003` Files: `docs/reference/configuration.md`, `tests/composables/useScrollytelling.test.ts`  
Before: Onepager global timeline behavior was implied but not formalized as a hard contract, and no regression test guarded full-page progress calculation.  
After: Documented onepager timeline contract explicitly: `--pm-scroll-progress` tracks full page scroll (`0 -> 1`) and scene-level progress is additive via `v-scrolly-scene` (`--pm-scene-progress`). Added regression test validating global progress across full page height.  
Upgrade impact: No breaking API change; scrollytelling contract is now explicit and CI-protected.

### 4. Shared Private-Teaching Domain Limits

`DOM-001` Files: `shared/domain/private-teaching.ts`, `server/utils/group-size.ts`, `app/utils/private-teaching.ts`, `tests/server/utils/group-size.test.ts`  
Before: No shared domain helper existed for private-group size normalization, leaving drift risk between runtime layers.  
After: Added shared limits/constants and `normalizePrivateGroupSize`, with server/app re-exports and tests.  
Upgrade impact: Future app/server implementations can reuse one normalization contract instead of duplicating clamp logic.

### 5. FAQ Rich HTML Render Safety

`FAQ-001` Files: `server/api/faq/index.get.ts`, `app/components/sections/SectionFaq.vue`  
Before: FAQ answers were rendered via `v-html` without explicit public API sanitization contract marker.  
After: FAQ public API sanitizes `answer` payload before response and component includes explicit safe-render marker comment at `v-html` site.  
Upgrade impact: Unsafe legacy FAQ markup is stripped more consistently; visible output may change only for unsafe content.

### 6. Sanitizer Fallback Correctness

`SEC-001` Files: `server/utils/sanitize.ts`, `tests/server/utils/sanitize.test.ts`  
Before: Fallback event-handler regex could remove only `on*=` token and leave malformed quoted residue.  
After: Event-handler fallback now removes full attribute expressions (`on*="..."`, `on*='...'`, unquoted variants), with expanded tests.  
Upgrade impact: Security hardening; malformed/unsafe inline handler markup is removed more strictly.

### 7. Developer Script Portability

`DX-001` File: `package.json`  
Before: Seed/init/workflow scripts invoked `tsx` CLI directly.  
After: Scripts now use `node --import tsx ...` for runtime portability in constrained shells/CI.  
Upgrade impact: Better reliability in environments where direct `tsx` execution is restricted.

### 8. Style System Contracts

`CSS-001` Files: `app/assets/css/common/text.css`, `app/assets/css/typography/variables.css`  
Before: Heading utility class contract and `--font-black` token were missing.  
After: Added heading utility set (`.heading-xs`...`.heading-xl`) and `--font-black`.  
Upgrade impact: Heading usage is deterministic and reusable in templates/components.

`CSS-002` File: `app/assets/css/ui/forms/inputs.css`  
Before: Vertical spacing chains were partially implicit and segmented-control pattern was not standardized.  
After: Added explicit stack/form/grid-to-actions spacing contracts and reusable segmented-control styles.  
Upgrade impact: More predictable form/page spacing and shared finite-choice UI pattern.

`CSS-003` File: `app/assets/css/ui/content/data-table.css`  
Before: Data tables defaulted to fixed layout and narrow action columns with edge-hugging cell padding.  
After: Switched to readability-first layout (`table-layout: auto`), added edge-safe cell padding, and strengthened desktop action-row stability/no-wrap defaults.  
Upgrade impact: Better table scanability and fewer clipped/wrapped actions in admin tables.

`CSS-004` Files: `app/assets/css/ui/forms/buttons.css`, `app/pages/admin/contacts.vue`  
Before: Primary/secondary buttons had weaker contrast guarantees in custom themes; icon action hover semantics were inconsistent; contacts delete actions used `text-danger` pattern.  
After: Added contrast-aware button defaults with explicit borders, explicit icon-ghost hover color feedback, and standardized delete icon buttons to `btn btn-icon btn-ghost btn-danger` with accessible labels.  
Upgrade impact: More robust visual contrast and consistent destructive-action behavior.

### 9. Header/Footer Width Mode Naming and Pairing Policy

`CFG-001` Files: `app/puppet-master.config.ts`, `app/composables/useConfig.ts`, `app/components/organisms/TheHeader.vue`, `app/components/organisms/TheFooter.vue`, `app/assets/css/skeleton/header.css`, `app/assets/css/skeleton/footer.css`  
Before: Header/footer width behavior had no precise, self-describing config key and caused confusion with full-page content width mental model.  
After: Canonical key is now `features.headerFooterWidthMode` (`'contained' | 'full'`) with exact semantics:
1. `contained`: header/footer inner content constrained + centered.
2. `full`: header/footer inner content edge-to-edge (no max-width).
3. Scope is header/footer inner chrome only (not main content width / not onepager timeline width).
Upgrade impact: Visual default remains contained inner chrome. Legacy alias `features.websiteChromeWidth` is still read for compatibility and mapped to canonical behavior.

`CFG-002` Files: `app/puppet-master.config.ts`, `app/composables/useConfig.ts`, `docs/reference/configuration.md`  
Before: No compatibility path existed for projects that already set `features.websiteChromeWidth`.  
After: Added backward-compatible alias fallback and documented deprecation path:
1. Canonical key: `features.headerFooterWidthMode`
2. Legacy alias: `features.websiteChromeWidth` (fallback only)
3. Planned alias removal target: `1.4.0`
Upgrade impact: No immediate break for existing configs; migration to canonical key is required before `1.4.0`.

### 10. Admin Navigation Alignment Contract

`NAV-002` Files: `app/assets/css/layout/admin-header.css`, `app/assets/css/skeleton/nav.css`, `tests/server/styles/style-system-contract.test.ts`  
Before: Admin nav alignment expectations were implicit and easy to drift between horizontal/vertical modes.  
After: Formalized alignment rules and added regression contract checks:
1. Horizontal mode (`admin-header-nav`) keeps nav cluster centered.
2. Vertical mode (`sidebar-nav`) keeps nav top-anchored and footer actions pinned to bottom (`margin-block-start: auto`).
Upgrade impact: No API break; admin UX alignment behavior is now explicit and protected.

`DOC-001` Files: `docs/entrypoints/framework-development.md`, `docs/entrypoints/greenfield-build.md`, `docs/entrypoints/brownfield-migration.md`, `docs/entrypoints/README.md`

`DOC-002` Files: `docs/roadmap/NEXT_CHAT_HANDOFF.md`, `docs/roadmap/eugenia-implementation-plan.md`, `docs/roadmap/implementation-log.md`, `docs/roadmap/implementation-log-archive.md`

`DOC-003` Files: `docs/architecture/1.1.0.md`, `docs/architecture/1.2.0.md`

### 12. Regression Contract Tests

`TEST-001` File: `tests/server/styles/style-system-contract.test.ts`  
Before: No targeted regression tests existed for newly mandated style contracts.  
After: Added style contract tests covering heading utilities, font token, spacing chains, segmented controls, table defaults, button/icon contracts, onepager full-bleed wrapper contract, and admin nav alignment contract.  
Upgrade impact: CI/test signal improves for style-system regressions.

`TEST-002` Files: `tests/e2e/auth-flow.test.ts`, `vitest.config.ts`  
Before: Auth-flow browser tests used unsupported matcher APIs for Vitest and ran against `pmMode: 'unconfigured'`, causing false failures/timeouts.  
After: Reworked browser assertions to Vitest-compatible checks, stabilized selectors/timeouts, and forced test runtime mode with `PM_MODE='build'` in Vitest env.  
Upgrade impact: `npm run test:run` now validates full auth-flow journeys in CI/local without false negatives.

`TEST-003` File: `tests/composables/useScrollytelling.test.ts`  
Before: Global onepager timeline contract (`--pm-scroll-progress`) had no dedicated regression coverage.  
After: Added composable-level regression test proving full-page timeline progression (`0 -> 0.5 -> 1`) across the complete document scroll range.  
Upgrade impact: Prevents silent regressions in onepager storytelling timeline behavior.

## Migration Cookbook (1.1.x -> 1.2.0)

### 1) Config key migration map

| Previous key | Canonical key (1.2.0+) | Compatibility window | Action |
|---|---|---|---|
| `features.websiteChromeWidth` | `features.headerFooterWidthMode` | Alias still read in `1.2.x` and planned for removal in `1.4.0` | Rename now to avoid future break |

### 2) Header/Footer width behavior table

| Scenario | 1.1.x behavior | 1.2.0 behavior | Project action |
|---|---|---|---|
| No key set | Implicit full-like/legacy chrome behavior | Canonical default `contained` | Set `headerFooterWidthMode: 'full'` only if you need edge-to-edge inner chrome |
| Explicit full-width preference | `websiteChromeWidth: 'full'` (legacy usage) | `headerFooterWidthMode: 'full'` (canonical) | Rename key to canonical |
| Main content/scrollytelling width | Often mixed with chrome assumptions | Explicitly separate from header/footer width key | No action unless project relied on ambiguous interpretation |

### 3) Quick verification checklist

1. Confirm your config uses `features.headerFooterWidthMode` (not only legacy alias).
2. Verify header/footer at desktop and ultrawide breakpoints:
   - `contained`: centered constrained inner chrome.
   - `full`: edge-to-edge inner chrome.
3. Verify onepager scroll timeline still progresses end-to-end:
   - global `--pm-scroll-progress` moves from `0` at top to `1` at bottom.
4. Verify section-level scrollytelling remains additive (scene effects do not break global narrative continuity).
5. Verify admin navigation alignment:
   - horizontal admin header nav cluster is centered,
   - vertical sidebar nav remains top-anchored.

## Upgrade Actions (Project Maintainers)

1. Pull framework update and install dependencies:
```bash
npm install
```
2. Rename legacy width key and keep behavior explicit:
```ts
features: {
  headerFooterWidthMode: 'full'
}
```
   Legacy alias `websiteChromeWidth` still works in `1.2.x`, but migrate now (planned removal target `1.4.0`).
3. If you had project-local mobile drawer overrides for hidden `.header-actions`, remove them and re-test mobile nav actions.
4. If you render FAQ answers from `/api/faq`, verify expected markup after stricter sanitization.
5. If your scripts rely on direct `tsx` invocation, align to `node --import tsx` pattern.
6. Run full validation:
```bash
npm run lint
npm run test:run
npm run build
```

## Contract Changes to Be Aware Of

1. Canonical config feature: `features.headerFooterWidthMode` (`'contained' | 'full'`), default `'contained'`.
2. Legacy alias `features.websiteChromeWidth` is still read as fallback in `1.2.x`; planned removal target is `1.4.0`.
3. Onepager scrollytelling contract is explicit: global timeline (`--pm-scroll-progress`) is end-to-end page progress; scene-level progress is additive (`--pm-scene-progress`).
4. Admin nav alignment contract is explicit by mode (horizontal centered, vertical top-anchored).
5. FAQ public answer payload is now sanitized before UI rendering.
6. New optional scrollytelling directives/hooks are available: `v-parallax`, `v-scrolly-scene` and `--pm-*` CSS variables.

## Breaking Changes

None intentional at API/schema level.

## Potentially Visible Behavior Changes

1. Header/footer inner chrome defaults to contained mode (set `headerFooterWidthMode: 'full'` for edge-to-edge inner chrome).
2. Unsafe inline-handler markup in FAQ/HTML content is removed more strictly.

## Known Follow-Up

1. Build/test logs may still show non-blocking warning that `clamscan` is treated as external when the dependency is not installed in the environment.
2. Downstream feedback package is tracked at `docs/releases/feedback/1.2.0-eugenialatuweb.md`; framework-side resolution is documented in `docs/architecture/1.2.0.md`.
