# Release 1.3.1

Date: 2026-03-10
Type: Patch (`1.3.0 -> 1.3.1`)

## Overview

Release 1.3.1 is a **documentation correction patch** for 1.3.0. This release fixes inaccuracies in the 1.3.0 release notes and changelog regarding API response envelope behavior, command references, and security documentation.

**No code changes** are required in existing 1.3.0 deployments. The implementation was correct; only the documentation contained errors.

## Correction Ledger

This release documents corrections to 1.3.0 documentation artifacts. Each correction is tracked with its source comment.

### Correction 1: Strict Envelope Claim Inaccurate for Empty Results

**Issue:** Several API endpoints returned raw arrays (`[]`) on empty results instead of the documented envelope format (`{ success: true, data: [] }`).

**Affected Files:**
- `server/api/blog/posts.get.ts`
- `server/api/faq/index.get.ts`
- `server/api/features/index.get.ts`
- `server/api/team/index.get.ts`
- `server/api/testimonials/index.get.ts`

**Fix Applied:** All empty-state responses now return `{ success: true, data: [] }` to match the strict envelope contract.

**Documentation Updates:**
- `docs/releases/1.3.0.md` — Updated to reflect actual behavior
- `CHANGELOG.md` — Updated to reflect actual behavior
- This file — Documents the correction

**Upgrade Action:** If you built client code against 1.3.0 that handles empty API responses, update your code to expect the envelope format:

```typescript
// 1.3.0 behavior (incorrect)
const response = await $fetch('/api/blog/posts?category=empty')
// response = []

// 1.3.1 behavior (corrected)
const response = await $fetch('/api/blog/posts?category=empty')
// response = { success: true, data: [] }

// Or use apiFetch composable for automatic unwrapping:
const posts = await apiFetch('/api/blog/posts')
// posts = [] (empty array, envelope auto-unwrapped)
```

### Correction 2: Incorrect Command and Composable References

**Issue:** Release 1.3.0 documentation referenced non-existent commands and composables.

**Errors Found:**

| Document | Incorrect Reference | Correct Reference |
|----------|---------------------|-------------------|
| `docs/releases/1.3.0.md` | `useApiFetch` composable | `apiFetch` composable |
| `docs/releases/1.3.0.md` | `node scripts/audit-api-envelope.mjs` | `npm run audit:api-envelope` |
| `CHANGELOG.md` | `scripts/audit-api-envelope.mjs` | `npm run audit:api-envelope` |
| `CHANGELOG.md` | "Automated CI validation for envelope compliance" | No CI enforcement exists |

**Fix Applied:** All references updated to match actual implementation.

**CI Enforcement Claim:** The 1.3.0 documentation claimed "Automated CI validation for envelope compliance." This was inaccurate — the CI workflow (`.github/workflows/ci.yml`) does not include envelope audit enforcement. This claim has been removed.

**Upgrade Action:** Use the correct command for envelope auditing:

```bash
# Correct command (from package.json)
npm run audit:api-envelope

# Optional: Run with enforcement (exits non-zero on issues)
npm run audit:api-envelope:enforce
```

For API client code, use the correct composable:

```typescript
// Correct composable (auto-unwraps envelope)
import { apiFetch } from '~/composables/apiFetch'

const portfolios = await apiFetch('/api/portfolios')
```

### Correction 3: Security Wording Misaligned with Implementation

**Issue:** Security documentation in 1.3.0 did not accurately reflect the actual encryption and signing key behavior.

**Errors Found:**

| Document | Inaccurate Wording | Correct Wording |
|----------|-------------------|-----------------|
| `docs/releases/1.3.0.md` | `S3_PROXY_SIGNING_KEY` required for private mode | Optional; falls back to `S3_SECRET_KEY` |
| `docs/releases/1.3.0.md` | Only `PM_SETTINGS_ENCRYPTION_KEY` documented | Also accepts `SETTINGS_ENCRYPTION_KEY` (legacy alias) |
| `CHANGELOG.md` | Incomplete security notes | Updated with accurate variable names |

**Implementation Reference:**
- `server/utils/secrets.ts` — Accepts both `PM_SETTINGS_ENCRYPTION_KEY` and `SETTINGS_ENCRYPTION_KEY`
- `server/utils/storage/s3-private-url.ts` — Uses `S3_PROXY_SIGNING_KEY` or falls back to `S3_SECRET_KEY`

**Fix Applied:** Documentation updated to match actual implementation.

**Upgrade Action:** No code changes required. Your existing environment variable configuration is valid:

```bash
# Both are valid (1.3.1 clarifies this)
PM_SETTINGS_ENCRYPTION_KEY=your-key
# OR
SETTINGS_ENCRYPTION_KEY=your-key

# S3 signing (optional override)
S3_PROXY_SIGNING_KEY=your-signing-key
# If not set, falls back to S3_SECRET_KEY
```
